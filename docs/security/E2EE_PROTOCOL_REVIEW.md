## 1. Frozen architecture checked

| Requirement | v1 disposition |
|---|---|
| Client-generated vault root secret | 32-byte CSPRNG VRS generated by authorized client |
| Per-device cryptographic identity | Local Ed25519 signing keypair; service receives raw public key only |
| Server ciphertext/minimum metadata only | Opaque IDs, public device material, wrapped material, ciphertext, versions/timestamps/authorization state only |
| Account authentication cannot derive health key | Account credentials are never KDF input for VRS/RS/TS |
| Trusted-device enrollment | Existing trusted device approves and transfers VRS through directly delivered high-entropy TS + HKDF/AES-GCM envelope |
| User-held recovery secret | Independent 32-byte CSPRNG RS wraps VRS through HKDF/AES-GCM |
| Loss boundary | Loss of all authorized device secrets and RS leaves old VRS unrecoverable; no administrator escrow |
| Revocation | Blocks future service authorization; no retroactive-erasure claim |
| Replay/tamper/substitution | One-use challenge/enrollment state, idempotency/revisions, Ed25519 signatures, AES-GCM AAD binding |
| Version agility | Protocol version + suite ID + key epoch; unknown suites fail closed; explicit migration |
| Dart/Web/Go implementation path | HKDF-SHA-256, AES-256-GCM and Ed25519 each have an implementation path in all three target environments |
| No bespoke primitive | v1 composes established KDF/AEAD/signature primitives; no custom cipher/hash/KEM/signature algorithm |

## 2. Primitive selection

Canonical suite:

`SREVA-AES256GCM-HKDFSHA256-ED25519-V1`

Selected primitives are HKDF-SHA-256 for key derivation, AES-256-GCM for authenticated encryption, Ed25519 for device request authentication, SHA-256 for request-body digests, and platform CSPRNG for VRS/RS/TS/salts/nonces/opaque IDs/challenges.

Implementation targets:

- Dart/Flutter: repository dependency `cryptography 2.9.0`;
- modern browsers: native WebCrypto `SubtleCrypto`;
- Go reference/service: Go 1.27.1 standard library.

The design intentionally avoids inventing public-key encryption. Trusted-device transfer uses a one-time high-entropy secret delivered directly by the user between devices; the service sees only an authenticated encrypted VRS envelope. HPKE can be reconsidered only in a future reviewed suite with maintained interoperable client support.

## 3. Why P-256 was removed from the candidate suite

The first candidate used ECDSA P-256/SHA-256. Exact-head workflow run `35164230362` on commit `cf2d68d079d3f8e43abaa271e08bfa34c7e38f10` isolated an implementation-path failure:

- WebCrypto P-256 vector verification: PASS;
- Go standard-library P-256 vector verification: PASS;
- Dart HKDF + AES-GCM envelope checks: PASS;
- Dart P-256 signature verification: FAIL with `UnimplementedError` from `DartEcdsa.verify`.

This did not prove P-256 cryptographically broken. It proved that the selected repository/runtime path did not satisfy Task 19's frozen three-client implementation requirement without introducing another backend/dependency. The minimal standards-preserving correction was therefore to change **only device authentication** to Ed25519. HKDF-SHA-256, AES-256-GCM, recovery, trusted transfer, framing, and server privacy boundaries remain unchanged.

The suite identifier changed because suite ID is deliberately authenticated/bound into KDF info and AAD. Consequently the deterministic envelope vectors were regenerated rather than relabeling old ciphertext under a new suite.

## 6. Key separation and server boundary

VRS, RS, TS, device signing private keys, and existing local-storage keys are independent roles. No password, email, phone, OTP, session token, or passkey credential becomes VRS/RS/TS input. HKDF info and AES-GCM AAD bind account/vault/enrollment/device/event/object/revision/operation/suite context. The server receives no VRS/RS/TS or health plaintext.

## 7. Nonce/key rules

AES-GCM requires nonce uniqueness for a key. v1 derives separate recovery, transfer, and per-event keys while still requiring fresh random 96-bit nonces. Production code must never reuse vector material. Retries resend the original immutable envelope; they do not re-encrypt under a reused event key/nonce. Recovery/transfer re-wrapping uses fresh salt and nonce.

## 8. Authentication and replay

TLS remains mandatory. Sensitive mutations bind account ID, device ID, method, path, single-use challenge, and SHA-256 request-body digest into a canonical transcript signed directly with Ed25519. Challenges are scoped, expiring, and one-use. Event IDs provide idempotency; same ID with changed bytes is rejected. Enrollment IDs are scoped, expiring, and one-use.

Ed25519 public keys use the raw 32-byte format and signatures use the raw 64-byte format. The protocol does not use Ed25519ph and does not add a second whole-transcript pre-hash.

## 9. Conflict/data-loss rules

The service cannot decrypt health content and therefore cannot choose a health-semantic conflict winner. Independent objects may converge. Stale/concurrent same-object updates are preserved instead of silently overwriting. Tombstone versus stale edit cannot silently resurrect data. Invalid/tampered remote data never replaces local authoritative health state. Local health capture continues during sync outage. `shared/sync/conflict-vectors/v1.json` records deterministic expectations.

## 10. Recovery and trusted-device transfer

Emergency recovery requires account identity authentication **and** the independent user-held RS. Server-stored recovery material is unusable for VRS decryption without RS. If every trusted device and RS are lost, support can recover identity but not the old encrypted vault.

Preferred new-device provisioning uses a direct one-time TS delivered by QR after explicit trusted-device approval. QR contains enrollment metadata + TS, not VRS or health plaintext. Production UX must use short expiry, source/target identity, cancellation, one-time consume, and secret clearing.

## 11. Compromise boundaries

Server/database compromise can expose ciphertext, wrapped envelopes, Ed25519 public keys, opaque IDs, sizes, timestamps, revisions, counts, and revocation state, but should not expose VRS/RS/TS/private signing keys/health plaintext. A malicious server can still deny, reorder, suppress, or delete service copies. Client compromise while unlocked remains outside what E2EE can hide from equivalent-privilege malicious code.

# Sreva E2EE Protocol v1 — Task-19 Review

**Review status:** IN PROGRESS until the exact final Task-19 branch head passes the three-client conformance workflow.

**Scope:** design review for the optional account/E2EE continuity protocol. This is an internal engineering gate, not a third-party cryptographic audit, certification, penetration test, or formal proof.

## 1. Frozen architecture checked

The proposed v1 design was reviewed against the frozen C2 architecture and Task-19 requirements.

| Requirement | v1 disposition |
|---|---|
| Client-generated vault root secret | 32-byte CSPRNG VRS generated by authorized client |
| Per-device cryptographic identity | Local ECDSA P-256 signing keypair; server receives public key only |
| Server ciphertext/minimum metadata only | Protocol limits server to opaque IDs, public device material, wrapped material, ciphertext, versions/timestamps/authorization state |
| Account authentication cannot derive health key | Account credentials are never KDF input for VRS/recovery/transfer |
| Trusted-device enrollment | Existing trusted device explicitly approves and transfers VRS using one-time directly delivered high-entropy TS + HKDF/AES-GCM envelope |
| User-held recovery secret | Independent 32-byte CSPRNG RS wraps VRS via HKDF/AES-GCM |
| Loss boundary | Loss of every authorized device secret and RS leaves old VRS unrecoverable; no administrator escrow |
| Revocation | Blocks future service authorization; no retroactive-erasure claim |
| Replay/tamper/substitution | Challenge/enrollment one-time state, event idempotency/revisions, signatures, and AES-GCM AAD binding |
| Version agility | Protocol version + suite ID + key epoch, fail-closed unknown suite, explicit migration |
| Dart/Web/Go implementation path | Same HKDF-SHA-256, AES-256-GCM and ECDSA P-256/SHA-256 primitives available in all three target environments |
| No bespoke cryptographic primitive | PASS by design: v1 composes standard KDF/AEAD/signature primitives; no custom cipher/hash/KEM/signature algorithm |

## 2. Primitive-selection review

Canonical suite:

`SREVA-AES256GCM-HKDFSHA256-P256-V1`

Selected primitives:

- HKDF-SHA-256 for domain-separated key derivation;
- AES-256-GCM for authenticated encryption;
- ECDSA P-256/SHA-256 for device request authentication;
- SHA-256 for request-body digests;
- platform CSPRNG for VRS/RS/TS/salts/nonces/opaque IDs/challenges.

Implementation targets:

- Dart/Flutter: existing repository dependency `cryptography 2.9.0`;
- modern browsers: native WebCrypto `SubtleCrypto`;
- Go service/reference: Go 1.27.1 standard library.

The design deliberately does **not** depend on the newly investigated Dart HPKE implementation. HPKE would be reasonable only after a separate maintained-library/interoperability review. v1 instead avoids a public-key encryption dependency for trusted-device transfer by using an explicit one-time high-entropy direct transfer secret. That secret is relayed device-to-device through the user's local QR action; the service sees only the encrypted envelope.

This choice reduces cryptographic dependency surface without weakening the frozen requirement that an existing trusted device authorize a new device.

## 3. Key-separation review

The following secret roles are independent:

- VRS: root for encrypted sync events;
- RS: user-held emergency recovery capability;
- TS: one-time trusted-device provisioning capability;
- device signing private key: service-action/device-authentication capability;
- existing device-local vault/storage key: local persistence protection.

No account password, email, phone number, OTP, session token or passkey credential becomes VRS/RS/TS input.

HKDF info and AES-GCM AAD use explicit domain separation and bind the intended account/vault/enrollment/device/event/object/revision/operation/suite context. This prevents the same raw secret from being intentionally reused without protocol context and makes metadata substitution detectable at decryption.

## 4. Nonce/key review

AES-GCM requires nonce uniqueness for a key. v1 derives separate keys for recovery, trusted-device transfer and each logical sync event, while still requiring fresh random 96-bit nonces.

Production rules:

- never reuse Task-19 vector nonces/secrets;
- generate fresh random event IDs/salts/nonces;
- reject altered duplicate event IDs;
- do not retry a new encryption under the same event ID/derived key; retries resend the original immutable envelope;
- recovery/transfer re-wrapping creates fresh salt and nonce.

## 5. Authentication and replay review

TLS remains mandatory.

For sensitive service mutations, a device also signs a canonical transcript containing account ID, device ID, method, path, single-use challenge and SHA-256 request-body digest. The server verifies session/account/device/challenge/body/signature atomically enough that challenge consumption cannot race into two accepted mutations.

Event IDs provide idempotency. Byte-equivalent retry returns the existing acknowledgement. Same event ID with different content is rejected.

Enrollment IDs and challenges are random, scoped, expiring and one-use.

## 6. Conflict/data-loss review

The service does not decrypt health content and therefore cannot make health-semantic conflict decisions. It can enforce opaque revision rules and preserve concurrent branches. Ambiguous conflicts are surfaced after client decryption.

Important safety rules:

- independent objects can converge automatically;
- stale same-object changes never silently overwrite a newer branch;
- tombstone vs stale edit never silently resurrects data;
- invalid/tampered remote data never replaces local authoritative health state;
- local health capture continues while sync is unavailable.

`shared/sync/conflict-vectors/v1.json` records deterministic protocol-state expectations for these cases.

## 7. Recovery review

Emergency recovery requires account identity authentication **and** the user-held RS. The server-stored recovery envelope is useless for decryption without RS.

The recovery code is high entropy rather than a human password; its human-readable format/checksum is an encoding/handling aid, not the entropy source.

If all trusted devices and RS are lost, support staff can recover account identity but cannot recover the old E2EE vault. This is a deliberate privacy/data-availability tradeoff and must be stated clearly in UX.

## 8. Trusted-device transfer review

The preferred path uses a direct one-time TS delivered by QR. Security depends on the user approving the intended device and keeping the active QR/TS private until consumed/expired.

The QR does not contain VRS or health plaintext. A stolen active TS plus account/enrollment access is security-sensitive, so production UX must use short expiry, explicit source/target identity, cancellation, one-time consume and secret clearing.

For remote recovery where direct pairing is impractical, the RS path is used instead of weakening transfer-secret delivery.

## 9. Server-compromise review

A complete server/database compromise may expose:

- ciphertext and wrapped VRS envelope;
- public device keys;
- opaque IDs;
- sizes, timestamps, revisions, event/device counts and revocation state.

It should not expose VRS/RS/TS/device private keys or readable health payloads. The design does not claim metadata hiding or availability against a malicious server.

A malicious server can deny, suppress, reorder or delete server copies. Local authoritative state and CycleVault backup remain the recovery boundary for availability.

## 10. Client-compromise review

E2EE cannot protect plaintext from malicious code or a fully compromised device while the vault is unlocked. Browser XSS/supply-chain/service-worker/malicious-extension risks therefore remain release-critical and are handled by later hardening gates. The protocol documentation makes no stronger claim.

## 12. Required negative tests in implementation tasks

Task 19 freezes contracts/vectors; Tasks 20–24 must implement and test at minimum:

- wrong VRS/RS/TS;
- ciphertext/tag/AAD tamper;
- account/vault/device/object substitution;
- used/expired challenge;
- used/expired enrollment;
- revoked device push/pull/approval;
- stale and duplicate event handling;
- conflicting updates and tombstone/stale-edit case;
- body/signature mismatch;
- unsupported suite/version/key epoch;
- recovery with account auth but no RS must fail to unlock old vault;
- failed decrypt/schema validation preserves current local state.

- recovery/enrollment usability-abuse testing;
- policy/store-disclosure update only when sync actually ships;
